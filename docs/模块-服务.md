# 模块：服务

> 代码：`runtime.py`（装配）、`monitor.py`（状态机）、`service_main.py`（SCM 入口）、`ocr_*`（识别）。
> 协议细节见 [协议-门户.md](协议-门户.md)。

## 1. 生命周期

| 事件 | 行为 |
|---|---|
| 开机 | 服务自动启动；网络未就绪时按退避重试，不退出 |
| 崩溃 | SCM 失败恢复：重启 5 s → 10 s → 30 s，`RESET_PERIOD` 1 天后计数重置 |
| 停止 | 处理 `STOP` / `SHUTDOWN` / `PRESTOP`：停监控线程、关 IPC、回收 OCR 子进程，退出码 0 |
| 配置变更 | IPC 写入后热加载（先确认旧线程退出，再重建监控器），无需重启服务 |
| 注销 / 切换用户 | 无影响（Session 0、LocalSystem） |
| 升级 / 卸载 | 由 CLI 先停服务，再动文件 |

**当前没有内部看门狗**：监控线程若意外死亡，服务不会察觉，也不会自愈——状态停留在最后一次的值，只有下一次 `monitor.start` / `reconnect` 才会重新拉起。这一条旧文档曾误记为"已实现心跳重建"，实际代码里没有，作为缺口记在 [待办.md](待办.md)。

线程安全相关（都有对应的回归用例）：

- `_stop_monitor(wait)` 返回真实结果：没退出就返回 `stopping` 并**保留线程引用**
- 旧线程仍存活时 `_start_monitor` 拒绝启动，不会出现第二个认证线程
- `monitor.stop` 只等 1 秒（客户端超时 5 秒）；服务停止与热加载等满 OCR 宽限（默认 35 秒）
- 线程退出时由 `_run_monitor` 的 `finally` 清引用

## 2. 监控状态机

`monitor.cycle()` 一轮完成：在线判定 → 门户探测 → 取码 → 识别 → 校验 → 登录 → 复检。

| 状态 | 含义 |
|---|---|
| `online` | `check_url` 返回 204 |
| `portal_unreachable` | 所有候选都探测失败（detail 带具体原因） |
| `reconnecting` | 走到了登录，但失败（detail 是 `result` 与 `msga`） |
| `config_missing` | 没账号，或密码密文与当前门户地址不匹配 |
| `stopped` | 监控已停 |

退避：`5, 15, 30, 60, 120, 300` 秒，300 封顶；同一失败原因按"每 10 次记一条"去重，不逐条刷屏。

取消语义：取码前后、校验前、登录前都检查停止事件；取消时返回 `stopped`，**不累加失败次数**。

## 3. OCR 子进程

**决策**：默认 `ocr.mode = "subprocess"`，服务按需拉起 `NetAnchor.Ocr.exe`，一次识别后退出，空闲超时回收。

**实测（2026-10-18，Python 3.14 + ddddocr 1.6.1）**：

| 形态 | 服务 WorkingSet | 服务 Private | OCR 工作进程峰值 |
|---|---|---|---|
| S1 仅核心模块 | 25.7 MB | 17.7 MB | — |
| S3 进程内 OCR 驻留 | 72.7 MB（峰值 92.5） | 144.4 MB | — |
| S3 OCR 子进程 | 25.9 MB | 17.8 MB | 87.2 MB |

结论：采用子进程。按需拉起的单次开销实测约 **0.5 秒**（进程启动 + 模型加载 + 推理），一次断网重连可接受。ddddocr 导入+初始化约 0.25 秒，单张识别 10–15 ms。

协议（stdin/stdout 二进制）：请求 4 字节大端长度 + 图片字节；响应 4 字节大端长度 + UTF-8 JSON `{"text": str, "error": str|null}`。

## 4. 进程与账户

| 进程 | 账户 | 会话 | 生命周期 |
|---|---|---|---|
| `NetAnchor.Service.exe` | LocalSystem | Session 0 | SCM 管理 |
| `NetAnchor.Ocr.exe` | LocalSystem | Session 0 | 服务按需拉起，空闲回收 |

服务不读 `%USERPROFILE%`、不依赖 HKCU、不写用户 AppData。

## 5. 服务侧 IPC

`service_api.py` 分发命令，读写都不要求提权（安全边界由凭据密文绑定门户地址承担，见 [架构 · 安全边界](架构.md)）。调用者是否提权只写审计日志（`netanchor.audit`）。

`status` 的返回包含：`state`、`last_check_at`、`next_check_at`、`consecutive_failures`、`last_error`、`portal_in_use`、`started_at`、`uptime_seconds`。
