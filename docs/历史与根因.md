## 二、安全模型修订：用绑定代替提权（2026-10-18）

### 为什么改

原 D4 规定"写操作要求 Administrators"。实践与评审后确认这个控制不成立：

- UAC 是**知情同意**型控制：它只弹一个"是否允许 NetAnchor-Campus 修改设置"，**不会显示"要把门户地址改成 xxx"**。
- 会被社工引导的用户照样会点"是"；不会中招的熟练用户则每次改设置都多一步。
- 真正危险的是**组合**：改门户地址 + 服务持有明文密码 = 可以把密码送到任意地址。

### 改成了什么

1. 凭据密文的 DPAPI **entropy 绑定门户地址指纹**（`portal_fingerprint`：候选地址、两个端口的规范化串）。
2. 请求改地址时，必须**同时提交密码**（原子操作）；否则返回 `reauth_required`。
3. 地址改完后旧密文不可解；如果绕过 IPC 直接改文件，加载时 `password_context` 与当前指纹不符，凭据直接判定为不可用（`credentials_ready() == False`）。
4. 写操作不再要求提权；调用者是否提权只记入审计日志（`netanchor.audit`）。

### 效果

| 攻击 | 结果 |
|---|---|
| 低权限进程静默把地址改成自己的服务器 | 服务没有可用密码，不会外发；状态变为"缺少凭据" |
| 低权限进程改密码 | 登录失败（DoS），拿不到旧密码 |
| 用户主动改地址 | 界面要求重输密码，保存后重新绑定 |

### 验收用例

- `test_portal_change_requires_password`：改地址不交密码 → `reauth_required`
- `test_portal_change_with_password_rebinds_ciphertext`：交密码后密文变化且可解
- `test_changing_portal_invalidates_stored_password`：手工改文件 → 密码不可用
- `test_secret_context_binding`：不同上下文无法解密

## 四、外部复审整改（2026-10-22，2026-10-26 更新）

外部复审在固定提交 `447c2f7` 上确认了 1 项 P1 与 6 项 P2。本轮只处理 P1（#1），其余保持待修，避免一次改动面过大。

### #1 客户端不验证服务端身份（P1）— 已修复

**原问题**：`INTERACTIVE` 的 DACL 用的是 `GRGW`，而 `GENERIC_WRITE` 在管道上包含 `FILE_CREATE_PIPE_INSTANCE`，普通用户可再造一个同名实例；客户端按名字直连、不校验对端，保存密码时可能把新密码交给冒充实例。

**修复**：

1. DACL 改为 `0x100083`（读数据 / 写数据 / 读属性 / 同步），去掉创建实例权限。
2. 服务端实例带 `FILE_FLAG_FIRST_PIPE_INSTANCE`，名字被抢占时启动失败并记日志。
3. 客户端改为 `CreateFile` + `GetNamedPipeServerProcessId`，发送前校验对端；不通过就不发任何字节。
4. 开发态用 `NA_IPC_INSECURE=1` 显式放行（`--console` 下服务是 `python.exe`、非 SYSTEM）。

**验证**：

- 冒充实例（当前用户身份）→ 客户端拒绝、冒充端收不到任何请求（`tests/integration/test_pipe_identity.py`）
- 预期镜像不匹配 → 拒绝
- 放行模式 → 正常往返（证明拒绝原因是身份而非链路）
- 真实服务（SYSTEM + `NetAnchor.Service.exe`）→ 默认安全客户端连接成功、`status=online`

**未采用的选项**：`PIPE_REJECT_REMOTE_CLIENTS` 在本机 Windows 10 21H2 上被 `CreateNamedPipe` 以 `ERROR_INVALID_PARAMETER` 拒绝（实测），因此未使用；远程访问由 DACL 排除 NETWORK/ANONYMOUS 主体来限制。

**残余**：拿到 SYSTEM 令牌的攻击者不受这层保护——那已经超出本工具的安全边界。

**2026-10-28 修订**：上述"校验对端令牌"的做法在普通用户下必然失败（`OpenProcess` 直接被拒），已改为向 SCM 核对登记信息，见第五节第一起事故。

### #2 停止超时后线程引用被清空（P2）— 已修复

**原问题**：`_stop_monitor` 在 `join(10)` 之后无条件把引用置空；而 OCR 子进程超时是 30 s，线程可能仍在认证。再点"启动"就会起第二个线程，出现并行认证。

**修复**：

1. `Monitor` 持有停止事件，并在**取码前后、校验前、登录前**检查取消；取消时返回 `stopped`，不累加失败次数。
2. `_stop_monitor(wait)` 返回真实结果：没退出就返回 `stopping`，**保留线程引用**。
3. 线程仍存活时 `_start_monitor` 拒绝启动，不会出现第二个认证线程。
4. IPC `monitor.stop` 只等 1 s（客户端超时 5 s），服务停止与热加载则等满 OCR 宽限（默认 35 s）；旧线程未退出时热加载直接放弃，保留旧配置。
5. 线程结束时由 `_run_monitor` 的 `finally` 清理引用，状态由 `Monitor` 的最终回调置为 `stopped`。

**验证**：`test_stop_with_blocking_ocr_keeps_thread_and_blocks_restart`、`test_cancel_during_validation_skips_login`、`test_cancelled_before_cycle_returns_stopped`；真实服务 `monitor.stop → stopped`、`monitor.start → running`。

### #3 凭据绑定失效后仍提交空密码（P2）— 已修复

**原问题**：`cycle()` 判断的是 `password or password_protected`，而不是"凭据是否真的可用"。地址变更后 `password_protected` 仍非空，于是继续探测、取码、校验，最后 `login(..., "")` 提交空密码，状态也不是 `config_missing`。

**修复**：

1. `cycle()` 改用 `Config.credentials_ready()`——校验 `password_context` 与当前门户指纹一致；不可用时直接返回 `config_missing`，不碰门户。
2. `_authenticate()` 入口再检查一次明文密码，缺失就抛内部信号 `_CredentialsUnavailable`。
3. 登录调用前保留最后一道检查：没有明文密码绝不调用 `login`。

**验证**：`test_cipher_bound_to_other_portal_returns_config_missing`、`test_empty_password_never_reaches_login`。

### #4 升级失败后不恢复原服务（P2）— 已修复

**原问题**：`_stop()`、结束客户端、删除旧备份、`copytree` 备份都在 `try` 之外。备份这一步抛异常时，服务已经停了，既不起回来也不回滚。

**修复**：记录升级前运行状态（`was_running`）；从 `_stop()` 之后的所有步骤放进同一个 `try`；失败时 `_restore_previous_install()` 还原文件，并**只在升级前是运行中时**才启动；恢复过程本身失败也逐条打印。

**验证**（`tests/unit/test_cli_upgrade.py`，注入文件系统失败）：备份阶段失败、复制新文件阶段失败、升级前服务已停止三种路径。

### #5 卸载不先关闭客户端，删除中断（P2）— 已修复

**原问题**：`uninstall()` 只停服务、删服务，没有结束托盘/OCR 进程；托盘占着 `NetAnchor.Tray.exe` 时 `_remove_tree` 耗尽重试后抛错，此时服务已删、目录残留，`--purge` 也走不到。

**修复**：停服务后先 `_close_running_clients()`；**先删文件、再删服务**；删除失败列出原因并返回 1。

**验证**（`tests/unit/test_cli_uninstall.py`）：顺序断言 `stop → close → remove → delete_service`；删除失败时不删服务；未安装服务但目录存在时仍能清理文件。

### #6 `--purge` 清理失败仍返回 0（P2）— 已修复

**原问题**：配置目录清理用 `shutil.rmtree(ignore_errors=True)`，随后无条件打印"已删除配置与日志"并返回 0。文件被占用时静默失败、谎报成功。

**修复**：改用带重试的 `_remove_tree()`；删除后再检查目录是否真的不存在；只有确认成功才打印成功。

**验证**：`tests/unit/test_cli_purge.py` 四种路径；真实文件锁下 `uninstall --purge` 退出码 1、目录保留，释放后退出码 0。

### 测试基建：非管理员也能跑

复审用普通令牌执行 pytest 得到 25 项 PermissionError，原因是测试里 `ConfigStore` 会顺手收紧 DACL。

- `ConfigStore` 新增 `apply_acl` 参数；非 ACL 用例用 `apply_acl=False`，不触碰 DACL
- 只有两个真正验证 ACL 的用例保留默认值，并在非提权环境下 `skip`（而不是失败）

这样外部审计用普通账户跑测试时，结果是"通过 + 少量 skip"，而不是一片红色错误。

## 五、现场事故复盘

### 5.1 打包内两个 `pywintypes` DLL（2026-10-27）

**现象**：服务 `RUNNING` 但 `\\.\pipe\` 里没有管道；托盘设置报"连接服务失败：系统找不到指定的文件"；多次启动托盘出现重复图标。

**根因**：`_internal` 里同时存在 `pywin32_system32\pywintypes314.dll`（PyInstaller 的 pywin32 hook 收集）和根目录 `pywintypes314.dll`（被二进制依赖分析从基础 Python 目录额外收集）。Windows 加载 `win32\win32file.pyd` 时解析到根目录那份，而 Python 侧的 `pywintypes` 用的是 `pywin32_system32` 那份——**同一个 DLL 两份加载，产生两个互不相等的 `pywintypes.error` 类**。

后果：客户端连上就断时 `ReadFile` 抛 `ERROR_BROKEN_PIPE(109)`，`except pywintypes.error` 因为类身份不同抓不住，异常穿出到线程顶层，IPC 服务端线程终止、管道消失，此后所有连接都报"找不到指定的文件"。

**修复**：spec 去掉根目录那份；服务端按错误码（109/233）而不是异常类判断；单个连接出异常不再终止服务端循环；托盘单实例。

**验证**：打包产物只剩一份 DLL；冻结服务实测"客户端连上即断"后管道仍在、后续请求正常。

### 5.2 客户端身份校验在普通用户下必然失败（2026-10-28，0.2.4）

**现象**：真机上托盘只要发 IPC 就报"无法确认服务端身份（需要 LocalSystem 且镜像为 NetAnchor.Service.exe）"。CLI 正常——它不走 IPC。

**根因**：校验读的是**对端进程令牌**（`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `OpenProcessToken`）。服务跑在 `LocalSystem` 下，普通用户（哪怕账户是管理员，只要令牌被 UAC 过滤）对 SYSTEM 进程调用 `OpenProcess` 直接得到 `ERROR_ACCESS_DENIED(5)`；代码把"打不开"和"身份不可信"混为一谈，于是校验恒为 False。

这是**结构性必然**：托盘本来就是给普通用户点的，而校验要求提权。此前所有验证都在提权上下文（或 `NA_IPC_INSECURE=1`）下进行，所以一直没暴露。

实测（同一段 ctypes 探测，两种身份）：

| 步骤 | 提权 | 非提权（`runas /trustlevel:0x20000`） |
|---|---|---|
| 打开管道 | ✅ | ✅ |
| `GetNamedPipeServerProcessId` | ✅ | ✅ |
| `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` | ✅ | ❌ `GetLastError=5` |

**修复**：改为向 SCM 核对登记信息，不再读对端令牌。普通用户有权查询服务状态与配置（改配置才需要管理员），实测三项都可读：`QueryServiceStatusEx`（进程 ID）、`QueryServiceConfig`（账户、影像）、`GetNamedPipeServerProcessId`。判定三项：对端 PID == 服务登记的 PID、账户属于 LocalSystem、影像名匹配。

**安全语义等价**：原来问"对端令牌是不是 SYSTEM"，现在问"对端是不是那个被 SCM 登记为 LocalSystem 的服务进程"。要冒充得能在 SCM 里登记一个 LocalSystem 服务（需管理员），再抢占管道名（DACL 已不给 `INTERACTIVE` 创建实例的权限，服务端还带 `FILE_FLAG_FIRST_PIPE_INSTANCE`）——两条路都要求管理员。

**顺带改的**：失败时返回具体原因（PID 不一致 / 账户不是 LocalSystem / 影像不符 / 服务未登记），不再一律"身份不明"。

### 5.3 托盘可观测性与 IPC 重连（0.2.4）

**背景**：

1. **托盘没有任何日志**：`console=False`、无 `sys.excepthook`、无轮询兜底。现场那次 `NetAnchor.Tray.exe` 崩溃（`c0000005` @ `ntdll.dll`，WER 里有 `FaultTolerantHeap` 记录，说明系统怀疑堆被写坏）只留下 WER 一条记录。轮询线程一旦抛非 `IpcError` 异常就静默死亡，表现为"图标还在、菜单还在、状态永远不动"。
2. **每 5 秒重建整棵菜单**：pystray 的 win32 后端在 `_update_menu()` 里 `DestroyMenu` + 重建原生句柄，而 `menu` 的 setter 本身就会触发一次 `update_menu()`——原代码每次刷新等于重建两次。轮询线程和消息循环里正在 `TrackPopupMenuEx` 的句柄是同一个对象，属于竞态。
3. **连续 IPC 请求约 5% 失败**：服务端只挂一个管道实例，处理完一个请求到建下一个之间有毫秒级空窗，客户端撞上就得到 `ERROR_FILE_NOT_FOUND(2)`，而 `_connect` 只对 `ERROR_PIPE_BUSY(231)` 重试（实测 20 次连续请求失败 1 次）。

**改法**：托盘写 `%LOCALAPPDATA%\NetAnchor-Campus\logs\tray.log` 并装异常钩子；轮询单次失败不终止；菜单只在内容变化时重建、图标按颜色缓存；连接对 `FILE_NOT_FOUND` 也在超时窗口内重试（仅当 SCM 报服务 RUNNING）。

**残余**：菜单重建仍发生在轮询线程，只是频率从"每 5 秒"降到"状态变化时"。彻底消除竞态要让 UI 完全单线程（自建消息循环或换掉 pystray），未做。那次 `c0000005` 的真实调用栈没有拿到（诊断用的 LocalDumps 只能对之后的崩溃生效，之后未再复现）。

### 5.4 门户地址被填成完整 URL，导致永不自动登录（2026-10-29，0.2.5）

**现象**：掉线后 `portal_unreachable` 连续 85 次、持续 6.5 小时，直到用户自己用浏览器登录才"恢复在线"。用户反馈：**重连一直是手动做的**。

**根因**：配置里 `portal.candidates[0].host` 是 `http://<host>/`，而 `_base()` 无条件拼 `f"http://{host}"`，得到 `http://http://<host>/` → `getaddrinfo failed`。`PortalCandidate` 只校验 host 非空，设置窗口把输入原样落盘。`pick_candidate()` 又把异常记在 DEBUG 级，状态只剩"所有门户候选均不可达"——看起来像断网。

**修复**：`normalize_host()` 剥协议头/路径/空白，只用于请求侧；**不改存储值**（host 参与凭据指纹，改了密码失效）；`PortalClient.last_probe_error` 把每个候选的失败原因写进状态与日志（按原因去重）。

**验证**：原配置未做任何修改，`probe` 3/3 通过；取码 797 字节 GIF；打包的 OCR 识别出 4 位文本，0.7 秒。

### 5.5 登录被拒 `userid error1`：配置学号错误（2026-10-30）

**现象**：URL 修好后，2026-10-30 12:09 的掉线终于走到登录环节，门户连续回 `{"result": 0, "msga": "userid error1"}`，十分钟内 10 次。

**定位**：三份独立证据对齐——

| 来源 | 学号 |
|---|---|
| 门户登录页下发的 `uid`（当前会话） | 正确的 12 位 |
| 旧实现 `config.json`（历史上能登录） | 同一串 12 位 |
| 本产品 `config.json` | 13 位，前 12 位在第 9/10/11 位不同 |

密码两边解出来一致、运营商一致、门户地址的变化属正常换址。**唯一对不上的就是学号**。

**修复**：用户在托盘设置里把学号改对（门户未变，密文绑定不受影响），热加载后立即 `result=1` → `online`。

**教训**：

- 这个错被 5.4 的 URL bug **挡了两周**：链路连登录都走不到，"学号错"一直没有机会显形。修 bug 要一层层剥。
- 诊断信息值得做：能定位靠的是门户登录页的 `uid` 与旧实现配置的交叉比对。若日志在 `userid error1` 时同时打印"提交的账号后缀"，本可以更快。

### 5.6 托盘拖住注销与关机（2026-10-30，0.2.7）

**现象**：Application 日志反复出现 `10001 下列应用程序试图否决关机: NetAnchor.Tray.exe`（10-29 13:39、21:44，10-30 00:57、12:00、12:08、12:10）。同期没有 `1074`/`6006` 记录——关机被卡住，用户手动结束托盘后才继续。

**根因**（两处叠加，都不是"故意否决"）：

1. **pystray 不处理会话结束消息**：它的窗口过程只映射 `WM_DISPLAYCHANGE / WM_STOP / WM_NOTIFY / WM_TASKBARCREATED`，其余交给 `DefWindowProc`。进程不会在 `WM_ENDSESSION` 时主动退出，系统只能等超时强杀。
2. **消息泵会被 IPC 堵住**：菜单回调在 pystray 的消息循环线程里同步执行，内部 `PipeClient.request` 最长等 5 秒，这期间 `WM_QUERYENDSESSION` 没人应答。

**修复**：托盘自建隐藏顶层窗口 `NetAnchorSessionEndWatcher`，`WM_QUERYENDSESSION` 回 TRUE 放行、`WM_ENDSESSION` 时停图标退出；菜单动作改到后台线程。

**验证**（真实注销会中断当前桌面，所以直接投递同样的消息）：`WM_QUERYENDSESSION` 返回 1；`WM_ENDSESSION(wParam=1)` 后托盘 **0.03 秒**退出；日志依次为"系统请求结束会话（允许）→ 会话即将结束，托盘退出 → 托盘已退出"。

**残余**：真实关机未在本会话验证，下次实际关机时看 Application 日志里是否还出现 10001 即可确认。托盘仍无崩溃自愈——结论是**不引入守护进程**（见 [待办.md](待办.md)）。
