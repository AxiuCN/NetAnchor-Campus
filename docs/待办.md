## 2. 未完成的功能

### P7 安装包（仅候选，未定）

**现状**：交付形式是 onedir 目录 + 管理员终端执行 `NetAnchor.Cli.exe install`。功能完整，但分发体验是"开发者式"的：需要手动复制目录、先开管理员终端、控制面板里没有卸载项、没有安装向导。

**候选方案（未验证，不作为承诺）**：`NetAnchor.Setup.exe`（PyInstaller onefile 内嵌 payload），双击 → 自身请求 UAC → 解压到临时目录 → 复用 `cli.install()`；同时写注册表卸载项。

**尚未验证**：安装器体积、UAC 与解压时序、失败回滚、卸载项维护、杀软误报。

**当前结论**：先维持 CLI 安装方式。

## 3. 已知缺口

### 监控线程没有看门狗

服务侧只有 SCM 在进程级重启（5/10/30 s）。监控线程若意外死亡，服务不会察觉也不会自愈——状态停在最后一次的值，只有下一次 `monitor.start` / `reconnect` 才会重新拉起。

（旧文档曾写"内部看门狗：心跳超阈值重建线程"，2026-10-30 核对代码确认**不存在**，已从文档删除。）

### 托盘没有崩溃自愈

托盘崩溃/被结束后不会自动回来，要等下次登录或手动双击。**决定不引入守护进程**：

- 与"不写包装器代替程序管理生命周期"的项目约束冲突
- 守护者本身也会死，最后通常落到计划任务/系统服务，故障面更大
- 服务在 Session 0 无法直接拉起用户会话的 UI，要 `WTSQueryUserToken` + `CreateProcessAsUser`，等于把"SYSTEM 任意拉起用户进程"引入项目
- 崩溃自动重启会抹掉现场，反而更难查

若将来确实需要，优先用系统原生的 `RegisterApplicationRestart`（WER 重启），而不是自写守护。

### 代理（TUN / 透明模式）

应用层已经硬性直连（`ProxyHandler({})`），系统代理（如 `127.0.0.1:10090`）对它无效。唯一的风险是 **TUN/透明代理**在 IP 层劫持校园网流量，那时应用层绕不过。

- 已评估"掉线时自动关闭系统代理"方案：**不做**。对我们自己的连接没有收益（本来就直连），且替用户改环境副作用大（服务是 SYSTEM、系统代理是每用户 HKCU、代理程序会重写回去）
- 若要改善，推荐只做**诊断日志**（检测到系统代理指向本机且端口不通时记一条），需要时再议

### 长周期观察

- 连续运行数天的稳定性与日志轮转验证（目前最长观测约 2 天）
- 真实关机时是否还出现 `10001 试图否决关机`（0.2.7 的修复只做了消息级模拟验证）

## 4. 明确不做

| 项 | 原因 |
|---|---|
| 多账号管理 | 非目标 |
| 注销接口 | 当前门户上三个端点都返回成功但会话不断，且注销不属于产品功能（只负责登录/重连） |
| 代码内守护进程 | 见上文"托盘没有崩溃自愈" |
| 在配置保存时强制规范化 host | 会让凭据指纹变化、密码失效；要收敛输入得先改 UI 口径（"改地址 = 重输密码"） |
