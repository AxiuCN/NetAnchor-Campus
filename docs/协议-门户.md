# 协议：Dr.COM 门户

> 门户外把地址是**部署配置**，不是常量：`portal.candidates[].host` 与两个端口都不写死。
> 本文件只写协议事实与实现口径；地址、端口、真实账号一律不出现。

## 1. 认证流程

```
IDLE
 └─ 每 check_interval_seconds：GET check_url
      204 ──────────────► ONLINE（继续睡）
      非 204 ───────────► 探测门户候选（GET http://<host>:<login_port>/，期望 200 且 Server 含 DrcomServer1.0）
                            全部不可达 ──► portal_unreachable → 退避 → 下一轮
                            有可用 ─────► 取码（<eportal_port>）
                                             │
                                             ▼
                                           OCR 识别
                                             │
                                             ▼
                             check_captcha（consumable：一次尝试只判一次）
                                   result == "1" ──► 登录 /drcom/login
                                                      result == "1" ──► 复检 check_url（204）──► ONLINE
                                                      否则 ──► 记录 msga → 退避
                                  否则 ──► 重新取码（≤ max_captcha_attempts 次）→ 仍失败则退避
```

硬性规则：

- 所有校内请求**显式直连**（`ProxyHandler({})`），不读系统代理、不读 `HTTP(S)_PROXY`。TUN/透明代理仍可能劫持，见 [待办 · 代理](待办.md)
- 网络失败（超时/拒绝/DNS）与协议失败（状态码、JSON 异常）分开记录，均不触发进程退出
- 退避：`5, 15, 30, 60, 120, 300` 秒阶梯，300 封顶；同一失败原因不做逐条刷屏日志
- 每次校验失败必须重新取码，不复用同一张验证码
- 登录被拒（密码错误、互踢、频控、账号不存在）**不再连续换码重试**，直接交给外层退避，避免放大失败次数

## 2. 接口

| 用途 | 请求 | 判据 |
|---|---|---|
| 连通性检测 | `GET check_url`（默认 `http://connect.rom.miui.com/generate_204`） | `204` |
| 门户探测 | `GET http://<host>:<login_port>/` | `200` 且响应头 `Server` 含 `drcomserver`（大小写不敏感） |
| 取码 | `GET http://<host>:<eportal_port>/eportal/?c=main&a=getCode&v=<ms>` | `200` + `Content-Type: image/*` + 非空 body |
| 校验码 | `GET http://<host>:<eportal_port>/eportal/?c=Portal&a=check_captcha&callback=dr<ms>&captcha=<4位>&_=<ms>` | JSONP `result == "1"` |
| 登录 | `GET http://<host>:<login_port>/drcom/login?callback=dr<ms>&DDDDD=<账号>&upass=<密码>&_=<ms>&0MKKey=123456&R1=0&R3=0&R6=0&para=00&v6ip=` | JSONP `result == "1"` |

补充事实（门户登录页 `Dr.COMWebLoginID_1.htm` 下发的字段，2026-10 实测的那套 AC）：

- `authloginpath = /eportal/?c=ACSetting&a=Login`、`authloginport = 801`、`authuserfield = DDDDD`、`authpassfield = upass`
- 运营商后缀表：`校园用户 @xyw`、`校园电信 @dx`、`校园联通 @lt`、`校园其他 空`
- 页面上还会带当前会话的 `uid`（**不带后缀**的账号）、`stime` / `etime`（会话起止时间）——排查"登录成功没有"时是有力证据

## 3. 响应与错误

登录响应是 JSONP（`callback({...})`），本实现用正则取 `{...}` 再 `json.loads`，解析失败按协议错误处理。

| `result` / `msga` | 含义 | 处理 |
|---|---|---|
| `result=1` | 登录成功 | 2 秒后复检 `check_url` |
| `result=0 msg=userid error1` | 账号不存在（或账号字段与 AC 记录不符） | 不重试，退避；检查配置里的学号与运营商后缀 |
| 其它 `result=0` + `msga` | 密码错误 / 互踢 / 频控等 | 同样退避；`msga` 原样进日志与状态 |

**注意**：`result=0` 不等于"没登上"。曾出现过"登录请求已建立会话、但响应仍回错误码"的情形，判定以随后的 `check_url` 复检为准（见 [历史与根因 · P6](历史与根因.md)）。

## 4. 主机名规整

`host` 是用户在托盘设置里手填的，实测遇到过填成完整 URL（`http://<host>/`）的情况。请求侧统一走 `normalize_host()`：剥掉协议头、路径、空白。

**存储值不规整**：`host` 参与凭据指纹（`portal_fingerprint`），改了会让已保存的密码失效。所以只在拼接请求 URL 时规整，配置文件保持原样。
